## What

Decide a site-wide "Updated" date convention for review pages. Right now there is none, and that blocked an acceptance criterion on #20.

## Current state

No review page carries any published or modified date. Checked across all review pages:

- no `Updated` string
- no `<time>` element
- no `datetime=` attribute
- no `datePublished` or `dateModified` in the `ld+json` `Review` blocks (they carry author, rating and publisher only)

The only date on a review page is the footer copyright line.

## Why this matters

CLAUDE.md rule 5 says "Updated dates change only when content actually changed." That rule presumes an Updated date exists. Issue #20 had an acceptance criterion to bump it, and there was nothing to bump — the advisory ended up carrying its own inline `Advisory added 2026-08-20` stamp instead, which is honest but does not tell a reader when the rest of the page was last touched.

Readers judging whether a motherboard review is current have no signal at all today.

## Decisions this issue needs

1. **Surface.** Visible copy, a `<time datetime>` element, `dateModified` in the existing ld+json, or some combination. Search engines read the structured-data form; readers only see the visible one.
2. **Placement.** Under the `<h1>`, next to the star rating, or in the footer of the article body.
3. **Two dates or one.** Published *and* updated, or updated only.
4. **Backfill policy.** Every review page needs an initial value. Where does it come from — git history of the file, or a single honest "first published" date for the batch? Guessing per-page dates would violate rule 5.
5. **Scope.** This is every review page, not just the AMD subset — plus arguably the `guide-*.html` and `best-motherboard-for-*.html` pages, which have the same gap.
6. **Maintenance rule.** What counts as a change worth bumping the date for. A typo fix should probably not.
7. **Enforcement.** Whether `scripts/validate.mjs` should gain a rule that fails a page with no date, or one whose date is in the future.

## Why `needs-plan`

Touches every content page on the site and adds new page furniture plus a schema decision. That is well past the 15-file tripwire and is a design decision no existing issue specifies. A human should settle items 1–6 before any implementation issue is written.
