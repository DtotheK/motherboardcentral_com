Two things follow.

1. On a review page, a wrong M.2 count sits in a table. On a vs page it becomes

   purchase. Same error, sharper harm. CLAUDE.md rule 1 is not satisfiable for a
   pilot built on today's data.
2. The DB and the review pages **agree with each other** everywhere I checked
   (spot-checked the four B650 ATX boards row by row). So the issue's criterion
   "zero contradictions against the two source reviews" would pass while the page
   was still wrong. That criterion is necessary but not sufficient, and the plan
   below adds the missing one.

Net: the design is fully settled below, and it is worth settling now, but the
**content pilot cannot ship on current data**. The PR this plan produces is
tooling + evidence, not pages. See D14 and CAUTIONS C1.

## DECISIONS

**D1. Generation approach → a zero-dependency Node generator in `scripts/`, whose
output is committed HTML. Not hand-authoring, not Astro.**
This is the issue's "main thing to plan". Hand-authoring cannot satisfy criterion
2 ("no hand-typed specs") — the moment a human types `3x M.2` into a vs page it
can drift from the DB. A generator makes the constraint mechanical. It is not
build tooling in the sense CLAUDE.md forbids: nothing runs at deploy time, the
deploy is still "push static HTML", and it sits in the same category as the
existing `scripts/validate.mjs` (zero deps, run on demand). Astro stays
unstarted; this generator is a straight port target when it does start.

**D2. Reading `motherboardDatabase` → slice the array literal out of
`js/main.js` and evaluate it in `node:vm`. Do not move the data.**
The DB is a `const` inside the `if (compareSlots && compareTableWrap)` closure
(`js/main.js:857`), so it cannot be imported. Extracting it to
`js/motherboard-data.js` would touch shared JS plus `compare.html`'s script tags
and risks breaking a live tool for a pilot's convenience — rejected. Slicing a
pure data literal is deterministic, and the existing tests already precedent
running `js/main.js` under `vm` (`scripts/compare-url-state.test.mjs`). If the
markers ever move, the generator throws rather than emitting a page — fail
closed, matching validate.mjs's stated philosophy.

**D3. URL scheme → `compare-<slugA>-vs-<slugB>.html`, slugs sorted
alphabetically, one file per pair.**
Groups with `compare.html`, and the slugs are the #80 slugs, so
`compare-<a>-vs-<b>.html` and `compare.html?boards=<a>,<b>` name the same pair
the same way. Alphabetical ordering makes the canonical direction mechanical —
B-vs-A never exists as a file, so the duplicate-content criterion is satisfied by
construction rather than by a canonical tag. There is no redirect layer in this
repo, so the slug is permanent; that is why it is being fixed up front.

**D4. Prose → hand-written per pair, stored in `scripts/vs-pairs.data.mjs`,
merged with DB values at generation time via `{a.m2Slots}` placeholders.**
The generator rejects any spec-shaped literal in a hand-written field (regex list
in step 4), so a spec can only reach the page through the DB. That is criterion 2
enforced by a test rather than by discipline.

**D5. Diff presentation → all rows always rendered; differing rows marked,
identical rows muted. No JS, no "winner" arrows.**
Collapsing identical rows would hide the most useful answer these pages give
("these two boards are the same except for X"). Muting keeps it crawlable.
No better/worse arrows: `compare.html`'s comparators (`wifi`, `lan`, `higherM2`,
`phases`, …) live inside the closure, and reimplementing them in the generator
creates two copies of the ranking logic that will drift. Superiority claims stay
in hand-written prose where a human owns them.

**D6. Spec rows → the compare tool's `specRows` list verbatim, ending with
"Our rating".**
Same source, same order, same labels as `compare.html`, so a reader moving
between the two surfaces never sees a discrepancy. Rating is included because
omitting a number the compare tool already publishes reads as hiding it; it is
excluded from the difference gate in D8.

**D7. Amazon links → extracted from the two review pages' existing `/dp/` hrefs
at generation time. A board without one is ineligible.**
Guarantees byte-identical links, adds no tag, edits no tag (CLAUDE.md), and makes
criterion 6 unfailable. 21 of 73 review pages currently carry a direct `/dp/`
link; the rest are `/s?k=` search URLs recorded in `validation-baseline.json`
(#4). Ineligible boards wait for their affiliate batch.

**D8. Pair eligibility → mechanical gate, no editorial judgement.** A pair
qualifies only if: identical `socket`, identical `chipset`, identical
`formFactor`, **and** at least 2 differing spec rows excluding Brand and Our
rating. Both boards must also pass D14. Identical-chipset is stricter than the
issue's "same price tier" because tier is unmeasurable for us (we publish no
prices — see #24) while chipset is in the data. B650-vs-B650E style cross-tier
pairs are a later widening.
The ≥2 rule exists because of thin content: on our current 16-row schema, ASUS
TUF Gaming B650-Plus WiFi vs MSI MAG B650 Tomahawk WiFi differs in **one** row
(power phases). A 300-word page on that is exactly the content Google's
helpful-content system is built to demote.

**D9. Pilot set → the qualifying pairs of two clusters, capped at 6.** Diff
counts computed from the DB (excluding Brand and rating):

| Pair | Differing rows | In pilot |
|---|---|---|
| MSI MAG B650 Tomahawk WiFi vs MSI PRO B650-P WiFi | 3 (M.2, rear USB, phases) | yes |
| ASUS TUF Gaming B650-Plus WiFi vs MSI PRO B650-P WiFi | 3 (M.2, rear USB, phases) | yes |
| MSI MAG B650 Tomahawk WiFi vs GIGABYTE B650 AORUS Elite AX | 2 (M.2, phases) | yes |
| ASUS TUF Gaming B650-Plus WiFi vs GIGABYTE B650 AORUS Elite AX | 2 (M.2, phases) | yes |
| ASUS ROG Crosshair X870E Hero vs ASUS ROG Strix X870E-E Gaming WiFi | 4 (rear USB, LAN, phases, audio) | yes |
| ASUS ROG Strix X870E-E Gaming WiFi vs GIGABYTE X870E AORUS Master | 4 (rear USB, LAN, phases, audio) | yes |
| MSI MAG B650 Tomahawk WiFi vs ASUS TUF Gaming B650-Plus WiFi | 1 (phases) | no — fails D8 |
| GIGABYTE B650 AORUS Elite AX vs MSI PRO B650-P WiFi | 1 (rear USB) | no — fails D8 |

Two clusters rather than one because the 60-day criterion otherwise cannot tell
"the format works" apart from "this price band gets traffic". All 14 boards named
have verified `/dp/` links (`docs/affiliate-asins.md`, batches #49/#52).
**None of these six can be published until D14 is satisfied** — three of the
X870E boards are in the error table above.

**D10. Page skeleton** (generator output, in order): head (gtag block, unique
title/description/canonical/og — CLAUDE.md rule 4), nav copied verbatim from a
review page with `compare.html` marked `active`, `<h1>A vs B</h1>`, 40–60-word
intro, "The short answer" (3 bullets), the diff table, "What the differences mean"
(150–300 words), "Get the A if…" / "Get the B if…", the sourcing sentence, two
"Check price on Amazon" buttons, links to both full reviews, a
`compare.html?boards=a,b` deep link, "More head-to-heads", footer copied verbatim.
No images: issue #42 is open about an 11.7 MB image payload and these pages do
not need one.

**D11. Sourcing sentence, fixed and identical on every page:** *"This comparison
is based on the manufacturers' published specifications. We have not tested
either board."* Satisfies criterion 5 and CLAUDE.md rule 2. It is emitted by the
generator, not typed per page, so it cannot be softened by accident.

**D12. Styling → inline styles emitted by the generator; `css/style.css` is not
touched.** The usual argument against inline styles (70 hand-maintained copies)
does not apply to generated output — one template, regenerate to change. And it
keeps the shared stylesheet off the diff, which is a CLAUDE.md tripwire.

**D13. Structured data → none on vs pages.** A two-product page has no clean
schema.org type. Marking both boards as `Product` with the `aggregateRating`
already published on the review pages duplicates review markup across two URLs,
which Google treats as a quality problem. Adding nothing costs a rich result we
were never going to earn; adding the wrong thing costs trust in the ones we have.

**D14. Publication gate → every row a vs page prints must be verified against
that manufacturer's own spec page, recorded with URL and date, before the page
ships.** This is the criterion the issue is missing. "Agrees with our own review"
is not verification when both come from the same table (see the finding above).
On today's evidence, **zero pairs pass**: three pilot boards are provably wrong,
and MSI/GIGABYTE/ASRock spec pages are not machine-readable, so an agent cannot
clear the rest. Hence D15.

**D15. Split → this issue's PR ships the machinery, the eligibility report and
the evidence. Pages ship under a follow-up issue once specs are verified.**
The alternative — hold everything until a site-wide spec audit lands — leaves the
issue's actual open question (generation approach) unanswered indefinitely, and
the audit itself is easier to scope once the report exists. Nothing in the
Phase 1 PR is reader-visible: zero HTML pages added or changed.

**D16. Merge posture → `needs-human`, no auto-merge.** New page type, new
tooling, and a plan that overrides part of the issue's acceptance criteria. Two
CLAUDE.md tripwires, independent of file count.

Every function below is pure and takes its inputs as arguments, so no test needs

## CAUTIONS

**C1. This plan does not ship the pilot pages the issue asked for.** It ships the
machinery and the reason. If you would rather publish now on today's specs, say
"as-published" and I will re-plan Phase 2 to run immediately — but be clear about
the trade: three of the six pilot pairs contain a value I have already shown to
be wrong, and the wrong value is the one the page is about.

**C2. The verification figures came from a summarising fetch of each ASUS page,
not from my own eyes on the rendered table.** The M.2 counts (3→4, 4→5) and the
TUF board's Wi-Fi 6E→6 are unambiguous. The rear-USB counts depend on how the
page groups ports and I have marked them "needs human recount". Do not edit the
DB from my table alone — re-read each URL first.

**C3. Only ASUS spec pages are machine-readable.** MSI and GIGABYTE returned 403
on this run; ASRock is JS-only; vendor PDFs are glyph-encoded. So D14 is not
agent-satisfiable for 3 of our 4 brands, and the spec audit needs a human with a
browser. That is the real constraint on how fast this feature can scale, and it
is worth knowing before anyone plans 50 vs pages.

**C4. Titles will exceed the ~60 characters Google displays.** "ASUS ROG Crosshair
X870E Hero vs ASUS ROG Strix X870E-E Gaming WiFi - MotherboardCentral" is ~99.
I kept full board names and the site suffix: truncation in a SERP is cosmetic, a
shortened board name is a spec-accuracy risk. Overridable if you disagree.

**C5. D2 slices a data literal out of `js/main.js` by string markers.** Any edit
to that line breaks the generator loudly (test failure, not a bad page). It is
the price of not moving the DB out of the closure, and moving it is the right fix
during the Astro migration, not now.

**C6. `motherboardDatabase` has 70 entries but there are 73 review pages.** Three
review pages have no DB row. `validatePair` throws for those boards, so they can
never enter a pilot silently — but it is a data gap worth its own look.

**C7. If `npm test` fails on files you did not touch, check `git ls-files`.**
There are currently ~6 untracked `scripts/tmp-*.test.mjs` scratch files in the
working tree from other branches; `node --test` picks them up.

**C8. The 60-day success criterion needs GA4 (`G-MN6VW6GV50`) and affiliate
reporting.** Neither is readable from this repo, so no agent can close that loop.
Phase 2 step 7 files the reminder; a human has to do the reading.

**C9. Do not link vs pages to #37's chipset-comparison page.** It does not exist
yet, and `validate.mjs`'s `broken-link` rule would fail the build. Link
`guide-sockets.html` instead until #37 lands.
