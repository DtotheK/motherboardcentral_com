# DECISIONS

**D1 — Do we ship at all, or block on a human fetching the vendor tables?
→ Ship, under D2's sourcing rule, with `needs-human` on the PR.**
Blocking delivers nothing and the issue is nine months of reader demand old. But
we do not paper over the gap: the PR body carries the probe table above verbatim,
so the reviewer knows exactly what standard the page was built to.

**D2 — Replacement sourcing rule. → Three tiers, applied per cell.**
- **Tier 1 — our own published pages.** `review-*.html` spec tables are already
  on the site and give *board-level* facts. Use them freely, but a board fact can
  only ever support a "minimum"/"some boards" claim, never a chipset guarantee.
- **Tier 2 — two independent reputable sources that agree.** A chipset-level
  value may be published only if **two independent** sources state it and agree.
  Neither may be a retailer, an affiliate blog, an AI summary, or a mirror of the
  other. Record both URLs per cell.
- **Tier 3 — anything else.** If sources disagree, or only one exists, the cell
  gets **no number**. It reads `Board-dependent — check the board` with a
  footnote naming the disagreement. **Never split the difference, never pick the
  more impressive value, never round two disagreeing sources into one claim.**

This is rule 1's "if still unclear, flag in the PR rather than guess" applied at
cell granularity rather than page granularity. It is stricter than it looks: on
the rows that matter most, Tier 3 is the expected outcome, and that is fine — the
page's value is telling readers *which* things are not chipset guarantees.

**D3 — Which rows survive? → 8 of the proposed 10, plus one new one.**

| Proposed row | Verdict | Why |
|---|---|---|
| Socket | **Keep** | Genuine chipset guarantee, uncontested |
| CPU generations supported | **Keep** | Guarantee, with a BIOS footnote (D17) |
| Graphics slot: PCIe gen and lanes | **Keep** | The whole reason readers come; expect "minimum" labels |
| Primary M.2: PCIe gen and lanes | **Keep** | Same |
| Chipset-provided PCIe lanes | **DROP** | Vendors count differently (usable vs total; AMD's "44 usable" X870E figure folds in CPU lanes, Intel quotes HSIO vs PCIe). Least actionable row, highest contradiction risk per unit of reader value |
| Max USB ports by class | **DROP** | A chipset maximum no shipping board realises. Publishing "up to 10x 10Gbps" tells a reader nothing about the board in front of them and invites exactly the "chipset max read as board spec" error the issue warns about |
| USB4 mandated / optional / absent | **Keep, promoted to its own row** | The single most reader-relevant 800-series difference, and it is a *tri-state*, which suits D4's vocabulary |
| CPU overclocking | **Keep** | Guarantee |
| Memory overclocking (EXPO / XMP) | **Keep** | Guarantee; note H810 (D17) |
| Memory type (DDR4 / DDR5) | **Keep** | Guarantee |
| Typical board price band | **DROP** | See D8 |
| *Boards we've reviewed* | **ADD** | Satisfies the issue's cross-link requirement inside the table instead of as a loose list, and gives the reader something concrete where the spec cell says "board-dependent" |

**D4 — How are board-dependent cells rendered so they cannot be misread?
→ A four-word vocabulary, defined in a legend directly above each table.**
Exactly four cell forms are allowed. No other phrasing.

1. **Bare value** (`AM5`, `DDR5`, `Yes`, `No`) — a chipset-level guarantee. Only
   permitted in the "What the chipset guarantees" table (D5).
2. **`<value> minimum — some boards run <higher>; check the board`** — a floor,
   not a guarantee.
3. **`Optional — only on boards that implement it`** — vendor-optional feature.
4. **`Board-dependent — no chipset-level figure we could verify`** — Tier 3.

Legend text, used verbatim above both board-dependent tables:
> **How to read this table.** A bare value is something the chipset itself
> guarantees. "Minimum" means the chipset sets a floor and individual boards may
> exceed it. "Optional" means the chipset allows the feature but does not require
> it. "Board-dependent" means we could not verify a chipset-level figure — check
> the specific board. Everything here is based on published specifications; we
> have not tested these chipsets.

**D5 — Table orientation, and how to keep it usable on a phone? → Chipsets as
rows, and each vendor gets TWO tables, not one wide one.**
`css/style.css:1099` gives `.spec-table` `width:100%` with **no `min-width`**, so
a wide table squashes on mobile rather than scrolling — a 10-column matrix would
be unreadable at 360px, and issues #41/#42 already exist about mobile and page
weight. Splitting is also the cleanest possible answer to D4: a reader cannot
mistake a value for a guarantee when the table it sits in is titled
"What depends on the board".

- **Table A — "What <vendor> guarantees":** Chipset | Socket | CPU generations |
  CPU overclocking | Memory overclocking | Memory type → 6 columns.
- **Table B — "What depends on the board":** Chipset | Graphics slot |
  Primary M.2 | USB4 | Boards we've reviewed → 5 columns.

Chipsets go in the first column because `.spec-table tbody td:first-child` is
already styled as a row header, and because `guide-sockets.html` sets that
precedent. Wrap every table in `<div class="compare-container">` (as
`guide-sockets.html` does) so it scrolls rather than clips if it still overflows.
**Do not add a `min-width` to `.spec-table`** — that is shared CSS and would
change every existing guide table on the site (tripwire).

**D6 — Do AM4 and LGA 1700 share the tables with the current generation?
→ No. Separate section, one reduced table per vendor.**
Putting a dead-end socket in the same grid as a current one implies they are
cross-shoppable, which is the opposite of true for AM4. The attribute semantics
also differ (AM4 is DDR4 and pre-PCIe-5.0 throughout, so half the Table B columns
would be a column of identical "No"s). Section heading:
**"Previous-generation platforms"**, with one combined table per vendor —
Chipset | Socket | CPU generations | CPU overclocking | Memory type | Boards
we've reviewed — and the PCIe/USB4 story handled in two sentences of prose above
it rather than as columns.

**D11 — Validator hazard: no two-cell table rows anywhere on this page.**
`scripts/validate.mjs:186` treats **any** `<tr><td>k</td><td>v</td></tr>` on a
page as a spec-table row. A two-column row keyed `Socket` would register a
page-level socket claim, and every later mention of a *different* socket — on a
page whose entire job is comparing four sockets — becomes a `spec-contradiction`
NEW finding that fails the build. All four tables here are 5+ columns, so
`ROW_RE` cannot match. **Keep it that way**: no small two-column summary table,
no two-column "at a glance" box, anywhere on the page. Same applies to rows keyed
`LAN` or `WiFi`.

**D12 — Glossary hazard: write speeds as "Gbps", never as bare "G".**
`js/main.js:2765` injects glossary tooltips into every `.spec-table td`, and the
`lan` term matches `10G` / `5G` / `2.5G` / `1G` — so a USB cell reading
"Up to 10G" (the phrasing `guide-sockets.html:162` uses) gets an **Ethernet
speed** tooltip attached to a USB number. Write `10 Gbps`, `20 Gbps`, `40 Gbps`.
This also keeps the validator's `BODY_TOKENS.LAN` (which matches `GbE` and
`N G Ethernet/LAN`) from reading a USB figure as a LAN claim. `DDR5`, `DDR4`,
`EXPO` and `XMP` tooltips will fire and are wanted — leave them.

# CAUTIONS

- **The biggest one: AC 1 is not satisfiable in this environment, and D2 is a
  deliberate relaxation of it.** If you would rather not publish chipset-level
  values sourced from agreeing third parties, the alternative is to allow-list
  `curl` for `amd.com` and `intel.com`, or to paste both vendors' chipset tables
  into this issue — either unblocks Tier 1 and the plan should then be revised
  before implementation. This is the one decision here I would most like a human
  to look at.
- **`guide-sockets.html:259` will become wrong the moment this page ships.** It
  says "all chipsets except A620 support CPU overclocking"; B840 breaks that.
  Issue #35 D3 flagged the same sentence and chose to avoid B840 entirely rather
  than touch it. I chose the opposite — include B840, flag the conflict — because
  a chipset comparison page that omits a shipping chipset is a worse failure than
  a stale sentence on another page. Step 11's follow-up is how it gets fixed.
- **Several of the most reader-relevant cells will read "board-dependent".** That
  is the honest answer and it is the point of the page, but it does mean the
  finished tables will look less decisive than the third-party pages the issue
  cites as evidence of demand. That is a deliberate trade, not an oversight.
- **Six of 19 chipset rows will have no internal links** (B850, B840, X670, H810,
  H770, H610 — we have reviewed no boards on any of them). B850 may pick up links
  if #35 merges first.
- **I did not verify a single chipset spec myself in this run**, by design — D2
  puts that work in step 2 where it is recorded per cell. The four contested cells
  named in step 3 are characterisations of *where sources disagree*, drawn from
  searches run today; treat them as pointers, not as values.
- **`.spec-table` has no `min-width`.** If the six-column tables still crowd on a
  narrow phone, the fix is *not* to touch `css/style.css` — it is to drop a column
  or split a table further. Shared CSS is a tripwire.
- **No prices appear on this page** (D8), which is a departure from
  `guide-sockets.html`. If price bands are wanted, that is a separate decision and
  a separate issue.
- File count is 4, no shared nav/footer/layout markup is touched, so the only
  tripwire in play is the unverified-spec one — which D2 trips on purpose, hence
  `needs-human` on the PR regardless of how clean the diff looks.
