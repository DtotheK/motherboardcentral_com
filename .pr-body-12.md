## What changed

`jobs/run-job.sh` buffered an entire run into one `.json` via `>` redirection.
Nothing was written until the job ended, so a running job could not be tailed,
and the only artifact was raw JSON.

- `--output-format stream-json --verbose`, piped through `tee`, so the log grows
  line by line during the run.
- The result event is extracted to a sibling `.txt` with
  `jq -rR 'fromjson? | select(type == "object" and .type == "result") | .result'`.
  `-R` + `fromjson?` skips interleaved stderr lines; the object guard stops bare
  JSON scalars (`42`) from erroring the filter.
- `echo "starting $JOB at $(date)"` / `echo "finished $JOB at $(date)"`.
- The pipeline status is captured rather than left to `pipefail`, so a failing
  job still produces its `.txt` and `finished` line before the real exit code is
  propagated.

## Acceptance criteria

**"tail -f on a running job shows activity"** — `jobs/run-job.test.mjs` spawns the
real script against a fake `claude` that models the CLI contract: plain `json`
holds output back until the run ends, `stream-json` emits as it goes. The test
then runs a literal `tail -f` on the log and asserts a `"type":"system"` event
appears while the child is still alive (`child.exitCode === null`), and that the
file keeps growing afterwards. Verified red against the old script, green
against the new one.

**"a human-readable .txt exists next to each .json"** — covered by three tests:
same stem as the `.json`, contents are the result prose with no `"type"` stream
events, and the `.txt` is still written when the job exits non-zero.
