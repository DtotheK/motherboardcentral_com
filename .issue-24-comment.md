## Blocked: the pattern as specified cannot be published compliantly. Relabelling `needs-plan`.

The issue body already says it should carry `needs-plan` ("this is a design decision the issue does not itself settle (placement, markup, styling)"), but the label was never applied — it is currently `agent-ok` only. I've added `needs-plan` and stopped without a PR.

Beyond the design gap, there is a harder blocker that I think changes what this issue should ask for.

### The blocker: Amazon forbids the price this pattern is built around

Every retailer link on this site is Amazon. Verified against the current tree today (2026-08-20):

```
$ ls review-*.html | wc -l
73
$ grep -l '\$[0-9]' review-*.html | wc -l
0
$ grep -oh 'https\?://[a-z0-9.-]*\(amazon\|newegg\|bhphoto\|microcenter\)[a-z.]*' review-*.html | sort | uniq -c
    210 https://www.amazon.com
```

73 review pages, 0 prices, and Amazon is the **only** retailer we link — 210 links, no Newegg, no B&H, no Micro Center. So "name the retailer and link the existing affiliate URL for that board" means Amazon in every case.

Amazon's Associates operating policies (https://affiliate-program.amazon.com/help/operating/policies, re-read 2026-08-20) do not permit that:

> "Product prices and availability may vary from time to time. Because prices for and availability of Products that you have listed on your Site may change, your Site may only show prices and availability if: (a) we serve the link in which that price and availability data are displayed, or (b) you obtain Product pricing and availability data via Creators API or PA API"

And where a price *is* shown via the API, it must carry an adjacent timestamp plus prescribed disclaimer text, and non-image content may be cached for **at most 24 hours** before a fresh API call.

A price hand-committed into `review-*.html` satisfies none of those conditions. It is not Amazon-served, it does not come from PA-API, and a static file cannot refresh every 24 hours. The acceptance criteria here — a human-verified price, date-stamped once, with a staleness window of N days — describe exactly the thing the policy prohibits. Proposing N is moot: the ceiling is 24 hours and it is not ours to set.

This is worth being blunt about because the downside is not a stale number, it's losing the affiliate account.

Note also that a 24-hour refresh cycle means server-side or client-side API calls with credentials, i.e. build tooling / a backend, which CLAUDE.md currently forbids ("do not introduce frameworks or build tooling unless an issue explicitly says so").

### What the research note actually demonstrates

The issue's own research is the second, independent argument against the pattern. Neither pilot board yielded a citable current price: MSI MPG X870E Carbon WiFi returned four contradictory aggregator figures ($329.99 / $324.99 / $349.99 / $354.99) with Amazon and Pangoly both 403-ing automated fetches; the ASUS ROG Strix Z890-E figure traces to a PC Guide article dated 2026-02-26, ~6 months stale.

The sourcing rule the issue proposes ("verified against the retailer listing itself at the time of writing") is the right rule, and it is unsatisfiable for us: the retailer listing is Amazon, and Amazon refuses automated reads. So the rule permits only prices a human eyeballs by hand, board by board, re-checked before every expiry — which is not a pattern an agent can maintain, and is the same manual burden that made the price go stale in the first place.

I agree with the issue's handling of the Q3 2026 price-increase reporting, and want to reinforce one point in it: the "at least 50%" figure is **PCB component cost**, not retail board price. Club386: "The primary reason is cited as a dramatic increase in PCB costs, which have risen by at least 50% this calendar year." It traces to a single supply-chain report (Board Channels via VideoCardz) and should not be published as fact.

### The decisions a human needs to make

I'm not designing around this, per the no-brainstorm rule. The open questions:

1. **Drop live prices, or build for them?** A compliant live price needs PA-API, credentials, a 24-hour refresh path and therefore build tooling. That is a separate, much larger issue and a direct CLAUDE.md exception. Worth confirming we even have PA-API access — it generally requires qualifying sales.
2. **Is a dated launch-MSRP anchor an acceptable substitute?** Manufacturer-announced MSRP with a manufacturer or named-outlet citation and an explicit "announced at $X on <date>" framing is a historical fact about the product, not a current-price claim, so it sits outside the price-display rule. It serves the reader-orientation goal but **not** the deal-traffic goal in the issue's "Why" section — it will never say "on sale now." If that trade is acceptable, this issue should be rewritten around it, and the affiliate-link criterion re-examined, since pairing an MSRP with a buy link invites reading it as the current price.
3. **If neither: close this and the downstream "Update deal note" issues.** The prerequisite framing in the issue is sound, so if the pattern can't exist, the dependents shouldn't be filed.

Everything else in the acceptance criteria I'd keep as-is whichever way this goes — the date stamp, "absent a verified price the note is omitted entirely," no MSRP presented as a current price, no placeholders, and the CLAUDE.md rule 5 handling of "Updated" dates.
