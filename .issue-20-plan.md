## DECISIONS

**1. Component — reuse the plain `<div class="info-box">`, add no CSS.**
No review page uses bare `class="info-box"` today (checked all 73). `info-box tip` is Pros, `info-box warning` is Cons, so the plain blue variant collides with neither, and it is already the site's "read this" box on guide pages (`guide-no-post.html:106`, `guide-bios-update.html:104`, `guide-am5-slow-boot.html:104`). This kills the `.info-box.advisory` question and, with it, the need to add a `--accent-red` design token to `css/style.css` — a site-wide design decision this issue does not specify. **`css/style.css` is not touched at all**, which takes the shared-template tripwire off the table for the styling.

**2. Placement — immediately before `<h2 id="specifications">`, on its own.**
Two reasons. Reader: it lands after the Overview paragraph explains what the board is, above the fold on desktop, without pushing the product shot down. Technical: `scripts/validate.mjs:231` only feeds prose *after* the first `</table>` into `checkSpecContradictions`, so a block placed before the spec table can never trip a `spec-contradiction` finding. `<h2 id="specifications">` occurs exactly once on all 35 pages (verified), which makes the bulk edit a single unambiguous anchor.

**3. No TOC entry, but the block gets `id="ftpm-advisory"`.**
A TOC entry would mean editing the sidebar `<nav class="guide-toc">` on 35 pages — nav markup, the exact thing the tripwire names. The `id` gives us deep-linking for free. `validate.mjs:64` skips `#`-refs, so no validator impact.

**4. The copy does not say "AM4" or "AM5", and does not say "every CPU this board supports".**
Two separate spec-accuracy traps:
- `BODY_TOKENS.Socket` in `validate.mjs:203` matches `\bAM(\d)\b`. Writing "AM4" on an AM5 page would read as a contradiction. Avoiding the tokens is belt-and-braces on top of decision 2.
- "covers every CPU this board supports" is **false** on `review-msi-meg-x570s-unify-x-max.html` and the B550 pages: X570 boards also run Ryzen 2000, which is outside the affected Ryzen 3000–9000 range. The copy names the CPU range and lets the reader match. This is CLAUDE.md rule 1.

**5. No AGESA version string anywhere. Confirmed, and now with a second reason.**
The issue already forbids it because published strings conflict. Independently: today's sources say the fixed firmware has been with partners **since around May 2026**, with Ryzen Embedded in July — so any wording keyed to "released after the 11 August bulletin" would also be wrong. The copy states no version and no date threshold. It tells the reader to read their board's BIOS release notes.

**6. Vendor link — the four general URLs from this issue body, keyed off the brand in the filename.**
Zero of the 35 pages contain any vendor URL, so the fallback branch of that acceptance criterion applies to all 35. Map (counts verified, they sum to 35):

| brand prefix | pages | URL |
|---|---|---|
| `asrock` | 4 | `https://www.asrock.com/support/Security.asp` |
| `asus` | 12 | `https://www.asus.com/security-advisory/` |
| `gigabyte` | 8 | `https://www.gigabyte.com/Support/Security` |
| `msi` | 11 | `https://csr.msi.com/global/product-security-advisories` |

I tried to fetch all four to confirm they list this advisory. **All four failed to verify** — MSI and GIGABYTE returned 403 to our fetcher, ASRock returned an empty body, and ASUS loaded but renders its advisory table with JavaScript so the list came back empty. Conservative consequence: **the copy links them but makes no claim about what is on them.** Link text is "MSI's security advisories", not "MSI's fix for this board". I am using these four rather than substituting support-download landing pages because these are the URLs a human already put in this issue, and I could not verify any alternative either.

**7. Second link — our own `guide-bios-update.html`, for the BitLocker step.**
That guide already carries a sourced BitLocker-recovery section (`guide-bios-update.html:122-125`, citing Microsoft's own recovery-overview doc). Linking it is more useful than repeating the detail 35 times, it is internal so `checkLinks` verifies it, and it is content we control.

**8. Date stamp — "Advisory added 2026-08-20", one pinned string across all 35 pages.**
The issue's example says 2026-08-19, but that was the day the issue was filed; nothing shipped that day. CLAUDE.md rule 5 says dates are honest, so the stamp is the date the copy PR is actually authored. Pin it once in the copy-approval PR and reuse the identical string in the bulk PR so the 35 pages never disagree. If the copy PR slips past 2026-08-20, change it there and match it in the bulk PR — the test in Task 4 asserts the exact string, so a mismatch fails loudly.

**9. Page-level "Updated" dates — OUT OF SCOPE for this issue. Filed separately instead.**
There is no `Updated` string, no `<time>`, no `datetime=`, and no `datePublished`/`dateModified` on **any** of the 73 review pages (the ld+json `Review` blocks have author, rating and publisher, but no dates). So the acceptance criterion "only bump the page Updated date" has nothing to bump. Adding one would be new page furniture on 73 pages plus a schema decision — a site-wide convention this issue does not specify. The advisory's own inline stamp (decision 8) gives the reader the honest date for the only thing that changed. Task 6 files the convention as its own issue.

**10. One copy block for all 35 pages — no separate AM4 variant.**
The uneven-coverage caveat ("Coverage varies by board, and we have not verified that a fixed BIOS exists for this one") is true and non-alarming on AM5 pages too, and it is the sentence that stops us implying a fix we have not checked. A single byte-identical string makes the bulk edit greppable and the test trivial; two variants would drift.

**11. Copy-approval page — `review-msi-mag-b550-tomahawk.html`.**
AM4 is the harder case: older CPUs partly outside the affected range, and the uneven-BIOS caveat matters most there. If the copy reads correctly on a B550 board it reads correctly everywhere. MSI is also the vendor whose support URL is least self-evident, so the link pattern gets looked at too.

**12. Scope stays at the issue's 35 pages. Three more AM4 boards are filed as a follow-up, not folded in.**
The filename regex misses three pages whose spec table says `Socket AM4`:
- `review-gigabyte-b450m-d3hp.html`
- `review-gigabyte-b450m-d3hp-wifi6e.html`
- `review-asus-rog-crosshair-viii-dark-hero.html` (X570 — the filename does not contain "x570")

These readers need the advisory as much as the other 35. I am *not* silently widening a scope the issue states explicitly, so Task 6 files them as their own issue with a socket-based selector. **If you would rather fold them into the bulk PR, say so and it becomes 38 pages — the file-count tripwire already fires either way and the plan needs no other change.**

**13. PR split — two PRs, both `needs-human`, neither auto-merged.**
As the issue itself proposes. PR 1 is one page and is a copy review. PR 2 is the remaining 34 and is mechanical. The test file lands in PR 2, not PR 1, because it asserts coverage of all 35.

**14. Corpus note.** The site now has **73** review pages, not the 70 quoted in the earlier comment. The AMD-matching subset is still exactly 35.

```js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import fs from 'node:fs';
import path from 'node:path';
import { fileURLToPath } from 'node:url';

const ROOT = path.resolve(path.dirname(fileURLToPath(import.meta.url)), '..');

const ADVISORY_OPEN = '<div class="info-box" id="ftpm-advisory">';
const DATE_STAMP = 'Advisory added 2026-08-20.';

const VENDOR_LINKS = {
  asrock: 'https://www.asrock.com/support/Security.asp',
  asus: 'https://www.asus.com/security-advisory/',
  gigabyte: 'https://www.gigabyte.com/Support/Security',
  msi: 'https://csr.msi.com/global/product-security-advisories',
};

/* Same selector the issue specifies: every AM4/AM5 review page by filename. */
const PAGES = fs
  .readdirSync(ROOT)
  .filter((f) => /^review-.*\.html$/.test(f))
  .filter((f) => /b550|x570|a620|b650|x670|x870/i.test(f))
  .sort();

const brandOf = (file) => file.replace(/^review-/, '').split('-')[0];
const read = (file) => fs.readFileSync(path.join(ROOT, file), 'utf8');

/* Slicing to the specifications heading also asserts the block sits above it. */
function advisoryBlock(html, file) {
  const start = html.indexOf(ADVISORY_OPEN);
  assert.notEqual(start, -1, `${file}: no advisory block`);
  const end = html.indexOf('<h2 id="specifications">', start);
  assert.notEqual(end, -1, `${file}: advisory block is not above the specifications heading`);
  return html.slice(start, end);
}

test('the AMD advisory scope covers at least the 35 pages issue #20 names', () => {
  assert.ok(PAGES.length >= 35, `expected >= 35 AMD review pages, found ${PAGES.length}`);
});

test('every AMD review page carries exactly one advisory block', () => {
  for (const file of PAGES) {
    const hits = read(file).split(ADVISORY_OPEN).length - 1;
    assert.equal(hits, 1, `${file}: expected 1 advisory block, found ${hits}`);
  }
});

test('the advisory carries the CVEs, the bulletin, the BitLocker line and the date', () => {
  const required = [
    'AMD-SB-7064',
    'CVE-2026-6726',
    'CVE-2026-6727',
    'Ryzen 3000 to Ryzen 9000',
    'save your recovery key first',
    'guide-bios-update.html',
    DATE_STAMP,
  ];
  for (const file of PAGES) {
    const block = advisoryBlock(read(file), file);
    for (const needle of required) {
      assert.ok(block.includes(needle), `${file}: advisory missing "${needle}"`);
    }
  }
});

test('each advisory links its own vendor and no other', () => {
  for (const file of PAGES) {
    const brand = brandOf(file);
    const expected = VENDOR_LINKS[brand];
    assert.ok(expected, `${file}: no vendor URL mapped for brand "${brand}"`);
    const block = advisoryBlock(read(file), file);
    assert.ok(block.includes(`href="${expected}"`), `${file}: expected vendor link ${expected}`);
    for (const [other, url] of Object.entries(VENDOR_LINKS)) {
      if (other === brand) continue;
      assert.ok(!block.includes(url), `${file}: links the wrong vendor (${other})`);
    }
  }
});

test('the advisory sits above the spec table, outside the validator spec-contradiction window', () => {
  for (const file of PAGES) {
    const html = read(file);
    assert.ok(
      html.indexOf(ADVISORY_OPEN) < html.indexOf('</table>'),
      `${file}: advisory must appear before the first </table>`,
    );
  }
});

test('the advisory names no AGESA version and no socket', () => {
  for (const file of PAGES) {
    const block = advisoryBlock(read(file), file);
    assert.ok(!/AGESA|ComboAM\d/i.test(block), `${file}: must not name an AGESA version`);
    assert.ok(!/\bAM[45]\b/.test(block), `${file}: must not name a socket`);
  }
});
```

## CAUTIONS

1. **No vendor page was verifiable from here.** All four URLs failed our fetcher today: MSI and GIGABYTE 403, ASRock empty body, ASUS loads but renders its advisory list client-side so it came back empty. They are almost certainly fine in a browser — 403 to an automated fetcher is bot protection, not a dead link — but **nobody has confirmed any of them actually lists AMD-SB-7064**. The copy is written so that does not matter: it links them as "security advisories" and claims nothing about their contents. Please click all four before approving the bulk PR. Same failure mode as the ROG-forum citation on `guide-no-post.html`.

2. **Decision 12 is the one to overrule if you want to.** Three AM4 boards (two B450, one X570 Dark Hero) are affected by the same CVEs and get nothing from this issue. I kept them out because the issue fixes its scope at 35 with an explicit command. One word folds them in.

3. **Decision 9 re-scopes an acceptance criterion.** The "Updated date" AC cannot be met as written — the furniture it refers to does not exist on any of the 73 review pages. I have replaced it with the advisory's own inline stamp and filed the real question separately. If you wanted page-level Updated dates as part of *this* work, say so and it becomes a third PR touching all 73 pages.

4. **New fact, not in the issue body: the fixed firmware reached partners around May 2026** (Ryzen Embedded in July), per TechSpot and igorsLAB today. That means a board BIOS carrying the fix may predate the 11 August bulletin, so the copy deliberately gives no date threshold — "read the release notes" is the only safe instruction. Everything else in the issue body checked out: bulletin AMD-SB-7064 dated 2026-08-11, CVSS 4.0 scores 8.5 and 8.3, local privileged access required, root cause in the TCG TPM 2.0 reference code, reported via Intel researchers.

5. **AGESA strings remain unverified and stay off the pages.** I made no attempt to verify them board by board, and neither should the implementer. If anyone wants per-board version strings, that is a separate issue with 35 manual verifications in it.

6. **Both PRs are `needs-human`.** 35 files is well over the 15-file tripwire, and although `css/style.css` is untouched, a repeated block on 35 pages is template-adjacent by nature. Neither PR should auto-merge.

7. **`npm test` is currently dirty from other branches.** Untracked `scripts/tmp-*.test.mjs` files in the working tree fail for reasons unrelated to this work. Task 4 step 3 says how to tell the difference; do not "fix" them as part of this issue.

8. **The date stamp is pinned to 2026-08-20 and asserted exactly by the test.** If the copy PR is authored later, change it in both the block and `DATE_STAMP` in the test. The test failing on a mismatch is the intended behaviour, not a bug.
